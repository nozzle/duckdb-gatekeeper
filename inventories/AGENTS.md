# Function policy inventories

When changing inventories or their audit/generation tooling:

- Treat the pinned `duckdb` submodule revision as the engine source of truth. Inspect its function registrations, parser rewrites, and macro bodies. Use `duckdb_functions()` to discover changes and cross-check coverage, never to generate an allowlist automatically.
- Keep function names lowercase, sorted, unique, and grouped by the serialized `function_name`. Review side effects, volatility, resource I/O, dynamic SQL/dispatch, catalog/session access, and macro/type/name collisions. A name is authorized across signatures: classify it by its most capable overload.
- Put reviewed local computation or embedded static data without resource or state effects in `compute`. Put resource access, mutation, dynamic dispatch, catalog/session inspection, current-time, and source-limited runtime-verified names in `elevated`. Treat volatility as elevated unless the exact pinned source proves purity by argument. Keep uncertain or unaudited names in `unreviewed`; both elevated and unreviewed names remain excluded from defaults.
- Keep core grouping in `core.json` consistent with its compute list. Keep extension classifications, source pins, and non-obvious review reasons together in `extensions/<duckdb-extension-id>.json`. Do not discard review notes when restructuring data.
- Keep the extension roster aligned with the pinned release, including explicit entries for extensions with empty groups. Review external extension sources at the exact revision in DuckDB's descriptor; generated extension-name inventories are not exhaustive.
- For initial reviews and every supported major/minor upgrade, compare runtime signatures before and after loading each available extension in a fresh database. Check overload changes to existing names as well as new names. Record the actual extension revisions and distinguish directly loaded, dependency-loaded, statically linked, lazy catalog-scoped, and proprietary registrations. Run the diff on patch upgrades too.
- Capture candidate snapshots separately from accepted baselines. Never replace a baseline merely to make the audit pass, or mark a version reviewed without completing the source review. An unchanged signature does not prove unchanged behavior. Document unavailable extensions and incomplete runtime coverage; the Python baseline is not a complete extension audit.
- Verify parser-generated operators, syntax helpers, and reviewed macros with both serialized SQL and executable SQL, since some names have no runtime catalog row. Explain source-backed exceptions rather than weakening audit checks broadly.
- Preserve source-only/runtime-only limitations, especially proprietary inventories such as MotherDuck. Function policy governs explicit caller-authored names; it does not authorize all binding-time behavior, loading, settings, replacement scans, or resources. Trusted attached-table implementations may use internal readers, and there is intentionally no reader-argument inventory.
- Run `python scripts/generate.py`, `python scripts/audit_inventory.py`, rebuild the extension, and run the full test suite after inventory changes. Update tests for intentional default-count changes and add focused policy regressions. Use the documented candidate-environment workflow for other versions; do not relax the supported-version pin just to capture a snapshot.

See [README.md](README.md) for commands and the version-update procedure. The migration scripts preserve provenance; Gatekeeper's inventories are canonical and must not be overwritten from Mosaic during ordinary maintenance.
